# xochitl 阅读器踩坑

Move 自带的阅读器 xochitl 不开源，排 EPUB 的方式和规范、和别的阅读器都不太一样。这一篇把它的脾气集中记下来：**事实是什么、我们怎么应对、验证到什么程度**。

- 大部分条目是上游设备增强项目 2026-08～09 在 Move 上踩出来的（那时书在 Move 上直接优化，2026-10 起改成在电脑上用本仓库优化）。CSS 和跳转那几批是在固件 3.28.0.172 上测的，系统更新后可能变。
- 已经做成 profile 字段的怪癖（注释回链、图标标号、背景图、漫画页边距等），字段和理由在[设备 · 怪癖 → 字段](devices.md#怪癖--字段)，这里只补来由和细节，不重复。
- 「验证」一栏：**真机** = 在 Move 上看过，或量过 xochitl 自己排出的 PDF；**推断** = 从现象或反编译推出来，没单独验证；**未复核** = 有过结论但后来存疑、没重测。
- **「我们怎么做」以现在为准**：2026-10-08 起 Move 的文字书**只修复**（profile `text_repair_only`），只另外保证注释能点（`repair_note_links`）和照 Send to Kindle 的规则统一（`kindle_rules`），见[排版 · 现在每个模式做什么](typesetting.md#现在每个模式做什么)。下面写「完整优化时」的做法，现在只用在漫画（和没开只修复的自定义模式）上；文字书上那些怪癖又会露出来。

## 先知道它怎么排书

导入 EPUB 时，xochitl 按当前排版设置把整本书排成一份 PDF（`<uuid>.pdf`），屏幕上显示的就是它（存储方式见[设备 · 附录](devices.md#xochitl-怎么存-epub-和阅读进度2026-09-29-真机摸底只读)）。

- 这份 PDF 每页 303×538pt，和屏幕 954×1696 同比例：**1px = 303/954 ≈ 0.318pt**。下文的 pt 都是这份 PDF 里的尺寸。
- 导入时就排（经网页上传的书，导入完 `.content` 里已经有 `pageCount`）；改字号、字体、页边距整本重排。
- 好处是很多事不用肉眼看：把这份 PDF 拷回电脑量就行，见最后的[怎么验证](#怎么验证不用肉眼)。

## 严格 XML：一处不合法，整章或整本不显示

xochitl 把 EPUB 当严格的 XML 解析，不像浏览器那样容错。出错时**不报错、只是悄悄少了内容**，所以最好的检查是比页数（见[页数对不上](#页数对不上就是有章没排出来)）。

| 事实 | 我们怎么做 | 验证 |
|---|---|---|
| **同一个标签上出现两个同名属性**（典型是两个 `id`）→ 这一章整章解析失败、一片空白。Calibre 转的 AZW3/MOBI 元素常同时带 `aid` 和 `id`，转换时再生成一个 `id` 就成了两个 | 每个标签只留第一个 `id`（`collapse_dup_id_attrs`），质量门也查；产物的 XHTML 一律修成合法 XML（[排版 · EPUB 3 规范整理](typesetting.md#epub-3-规范整理)；只修复也做） | 真机（《消失的爱人》长篇只排出 7 页） |
| **OPF 不是合法 XML**（书名里混进一个 `\0` 就够）→ 整本只排出 1 页；日志里只有 `Asked for unknown item ""`，看不出原因 | OPF 输出合法 XML，质量门查 | 真机（2026-09-23，一本 PDF 转来的书，书名按 UTF-8 误解出 `\0`） |
| `<p id><p>…</p></p>` 这类无效嵌套成串挨着时，xochitl 自动闭合多出一个 `</p>`，**吞掉或合并一条** | 注释容器用 `<div>`，不往 `<p>` 里套块 | 真机（08-30，多看格式注释"少一条"） |
| 写在 `</body>` 之后的元素，`id` 不登记，指过去的链接点不动 | 往页面里插内容一律插在 `</body>` 之前 | 真机（08-21） |
| 流式 zip（本地文件头里不写大小、靠末尾的数据描述符）的 EPUB 打不开 | 重新打包。`EpubWriter` 写到可回写的文件，大小写在本地文件头里，产物应该不受影响 | 真机（原书打不开、重打包后正常）；我们的产物是推断 |

| 每章开头一张的装饰图（横幅、logo）是正常内容 | 不做"跨章重复图"去重（上游误删过一次，用户照片纠正后撤回） | 真机（用户确认） |

## 墨水屏刷新（波形）

Move 翻页时的刷新方式**跟页面内容走**，不是整机固定一档（2026-09-01 真机，同一本漫画关掉"翻页清残影"后肉眼对比）：

| 页面内容 | 刷新 |
|---|---|
| 彩色 | 最重：整屏黑白闪好几下，慢 |
| 256 级灰 | 中等 |
| 不超过 16 级灰（抖动） | 轻，快 |
| 1 位黑白（抖动） | 最轻最快 |

- **只对纯图页有效**：有文字的页，字是 xochitl 自己带灰边（抗锯齿）画的，整页仍走灰度那一档。文字书没有从内容上减闪的办法（推断）。
- 16 级灰的样本用 JPEG（质量 88）编码后也触发了轻档，面板看的也许是色调复杂度、不是严格的级数（推断）。真要做，少级灰度应存 PNG。
- 抖动不省体积，反而更大（抖动图压不动，《镖人》283→687MB）。
- 本仓库现在 `xochitl` 模式保留彩色（用户定），黑白屏模式转 256 级灰、不抖动（[排版 · 漫画](typesetting.md#漫画)）；降灰阶减闪没有做。

| 书架上显示的书名取 EPUB 里的 `dc:title`，不是上传的文件名（PDF 才用文件名） | 真机 |

| 开着云同步时，每导入一本书，xochitl 马上把书连同排出的 PDF 传到云上（出站约 0.8–1.9MB/s，持续 2–3 秒）；弱热点上传书会显得卡 | 真机（09-04；09-29 摸底时用户已关云同步） |
| **已经排过版的书原地换文件不可靠**：覆盖 `.epub`、删掉排版缓存后，xochitl 仍显示旧内容，重开也一样 | 真机（08-22《喜鹊谋杀案》）；10-09 经书架服务原地替换没复现（见下一段） |

**`booklib sync` 怎么传 Move**（2026-10-07 起）：经 SSH 端口转发调 Move 上书架服务的导入接口，流程见[使用指南 · 产物放在哪](usage.md#产物放在哪)和[架构 · 生成](architecture.md#生成sync-的第二步generaters)。用到的接口：

| 接口 | 做什么 |
|---|---|
| `POST /import?name=&folder=` | 新加一本，马上回任务号；超过上传上限的自动走下面的占位 + 磁盘替换 |
| `POST /import?uuid=` | 原地替换（保留 uuid、文件夹）；这本正在替换时回 409（旧版 400），booklib 等它做完再交 |
| `GET /import/jobs/<号>` | 查任务进度，做完回 uuid |
| `POST /import/states` | 一次查一批 uuid 还在不在（没删、没进回收站；2026-10-09；旧版没有时退回逐本 `GET /import/<uuid>`） |
| 回收站队列 | 删书（能恢复） |

**2026-10-09 真机**：《绍宋》排过版、开着的时候原地替换两次，再打开都是新内容 ✓（xochitl 先把开着的书关掉，再打开时重新排版）；进度由书架服务找回，见[设备 · 重拷书以后进度还在不在](devices.md#重拷书以后进度还在不在)。

**2026-10-07 真机（sync 38 本）**：按层建文件夹 ✓（xochitl 的 `createCollection(上级 uuid, 名字)` 传非空上级能建进上一级：「漫画」里的「死亡筆記(愛藏版)」「哆啦A夢」「北鬥之拳(究極版)」）；异步导入 ✓（38 本全部加入、记录齐全、无重复）；同一文件夹同字节认回 ✓（《阿加莎全集》上一轮没记下的那本被认回原 uuid）。原地替换 10-07 时还没在真机上走到（这一轮都是新加）；10-09 已走到（见上一段）。

**超过上限的大书：占位 + 磁盘替换**（上游的做法，要在 Move 上运行能写书库目录的程序；书架服务的导入接口用它）：

1. 先经网页上传一个几 KB 的占位书，让 xochitl 建好条目。**占位要带真书名和真封面**：书名和缩略图在导入时定下，替换后不会更新。
2. 在磁盘上把 `<uuid>.epub` 原子替换成真书，删掉占位的 `<uuid>.pdf`、`<uuid>.epubindex`。不用重启 xochitl。
3. 第一次打开时 xochitl 自己重新排：146MB 约 25 秒；156.5MB 约 74 秒排出 349 页。之后走缓存。
4. PDF 还要同时改 `.content` 里的 `pageCount`、`originalPageCount`、逐页 UUID 表、`redirectionPageMap`、`sizeInBytes`；列表里的页数打开一次才刷新。

真机验证过 154MB 的 PDF、153MB 的 EPUB（2026-09-20）。这和上一行"原地换文件不可靠"看起来矛盾，推断区别在于占位书还没被打开过、xochitl 内存里没有它的排版，没验证。

**手工删书**：xochitl 运行时直接删文件会被它写回去。要 `systemctl stop xochitl` → 删 `<uuid>` 目录和 `<uuid>.*` → `systemctl start xochitl`（2026-09-30 删测试书时这样做的）。`sync` 删书不走这条，经书架服务进回收站。

**停掉 xochitl 有概率让整机重启**：xochitl 退出时自己有概率崩溃（上游收集到 5 份崩溃栈，其中 3 份反编译看是退出时数据先析构、刷新屏幕的线程池后停），崩了会触发系统的应急处理、整机重启（会自己回来，没丢过数据）。照上面[手工删书](#传书与上传)停掉 xochitl 时要知道这一点。真机（2026-09-20～09-25，装着上游扩展的 Move 上多次）；"跟扩展无关"是反编译推断。

## 超大的书：打开要算一分多钟，会被当成卡死

几万页的合集，打开时 xochitl 的主线程要连续算一分多钟。系统的看门狗规定它 60 秒没响应就当卡死、强制杀掉重拉，用户看到的是"一打开这本书就重启"（整机没重启，重启的是 xochitl；日志 `xochitl.service: Watchdog timeout (limit 1min)!`）。2026-10-15 真机，固件 3.28.0.172：

| 书 | 正文 | 页数（缺省排版） | 结果 |
|---|---|---|---|
| 《梁羽生武侠全集》 | 55MB，1454 个 xhtml | 40492 | 打开就被杀（复现两次） |
| 《古龙作品全集》 | 54MB，1507 个 | 28128 | 被杀过 |
| 《金庸全集（旧版）》 | 34MB，170 个 | 14809 | 被杀过一次 |
| 《金庸作品集》 | 28MB，580 个 | 12637 | 打开、改字号都正常 |

| 事实 | 我们怎么做 | 验证 |
|---|---|---|
| **卡的是全书总量，不是单章太大**：上面几本单个 xhtml 都不超过 330KB。临界大约在一万多页、正文三十来 MB（只有四本书，粗估） | 不拆书（用户定：不想把全集拆成单部）。要稳就按部拆成几千页以内的书 | 真机 |
| **不是死循环，算完就好**：上游临时关掉看门狗（`systemctl service-watchdogs no`），《梁羽生》开书时主线程满负荷算了约 66 秒，之后正常翻页。采样 `/proc/<pid>/task/<pid>/stat`：一直是 R、用户态 CPU、几乎没有系统调用、内存平稳（约 545MB），不是等磁盘、也不是内存不够 | 上游把 xochitl 的看门狗放宽到 300 秒（装在 xovi 的服务目录里，整机重启生效），《梁羽生》真机能打开。**没装上游的 Move 仍是 60 秒**，这几本照样打不开 | 真机 |
| 页数和计算量跟着排版设置走：改字号、页边距会整本重排，耗时多半比开书还长 | 超过 300 秒照样会被杀；没测过 | 推断 |
| 被杀的那一刻 memfault 抓到的栈只有两三帧，落在不相干的代码上（Qt 注册类型那段），**看不出卡在哪** | 定位靠上面那种 `/proc` 采样，别信这个栈 | 真机 |

## 页数对不上，就是有章没排出来

严格 XML 出错时 xochitl 不报错，只是少排几页甚至整章，所以**比页数**是最省事的检查：

- 默认排版设置下，**中文每页约 460 字，英文每页约 960 个字符**（上游两本真书，估算和实际比 0.99）。期望页数 = 正文字符数 ÷ 每页字符数，跟 `.content` 里的 `pageCount` 比。
- **实际不到期望的一半，就当有章没排出来**：好的测试书 25/29 页，带 3 章双 `id` 的坏书只有 10/29 页；那本书名里有 `\0` 的书只排了 1 页。
- 漫画字少，估出来只有两三页，这个比法没意义。改了字号等设置，每页字数跟着变。
- 日志里的 `pdfrenderer_unix.cpp:141 logErrors` 平时就有成百条，多是噪声；`epubindex … failed to open` 也是良性的。看页数，别看这些日志。

## 怎么验证（不用肉眼）

| 想确认 | 方法 |
|---|---|
| 版面、图的位置大小 | 把 `<uuid>.pdf` 拷回电脑，PyMuPDF 读 `page.get_image_info()[0]['bbox']` 拿图的真实位置（别量非白像素，会把画面自己的留白算进去）；量每段首行的 x 偏移看缩进；比每页行数、行距 |
| **正文链接能不能跳** | 读那份 PDF 的跳转目标表（catalog 的 `/Dests` 名字树），每个链接的目标名都要在表里，再比对目标页的文字；PyMuPDF 的 `get_links()` 里命名目标是好的，`URI`/`launch` 是被当成外链的 |
| 目录跳到哪页 | 读 `<uuid>.epubindex`：Qt 二进制，每条是 u32 字节长 + UTF-16BE 的 `OEBPS/…#锚点` + u32 页号（从 0 起） |
| 书排全了没有 | `.content` 的 `pageCount` 跟期望页数比（上一节） |

- **目录和正文链接是两套机制**：上游曾拿 `.epubindex`（目录用的）核对正文链接、得出"能跳"，用户一点不跳。两样都要过才算能跳。
- **诊断书**：一本小 EPUB，每页只改一个变量、旁边放一段对照，投上去量排出的 PDF。CSS 覆盖类的写法连着几次都无效时，别再换写法，改成只动结构（比如去掉 `body` 的类）。
- **有在真机上生效的活样本，先拆开看它怎么写的**，比凭空造几版诊断书快（上游的缩进问题就是这样绕了远路：《飘》自带的外链 `p{text-indent}` 早就是答案）。
- 看不到屏幕别猜观感：让用户拍照，或直接说看到了什么。
- 测试副本先改掉 `dc:title`，免得和原书同名、点错本。
- 要读 xochitl 的界面代码：二进制里的 Qt 资源是 zstd 压缩的，扫魔数 `28 b5 2f fd` 逐块解压，含 `import Qt` 的就是 QML 源（3.28.0.172 上 553 个文件）；`strings` 要带上 UTF-16LE。

## 所有 em 换算都按缺省字号（2026-10-15 真机，《梁羽生》卷名竖排）

xochitl 的阅读字号（`.content` 的 `textScale`，设置里「文字与布局」）缺省 1.0；本仓库所有 em 换算（profile `em_px` 37.8、`horizontal_scale`、竖直间距换算、卷名这类**靠 em 外边距压窄的块**）都按缺省字号标定。字号调小以后，em 外边距跟着变小、压窄的框变宽：《梁羽生》卷名「女帝奇英传」靠左外边距 18.88em 压成一字宽的竖条，`textScale = 0.8` 时框宽多约 143px，一行放 4 个字、不再竖排（设备上 26965 页，缺省字号 40458 页）。Kindle 的行距、边距同样按字号换算，只是卷名这种靠 em 外边距撑出的窄框在 Move 上更脆（Move 不认块的 `width`、% 外边距坏）。2026-10-15 对窄的定宽块（卷名竖排）换了写法（KINDLE_RULES 38）：包进单格表格、表格 `width="14%"` `align="right"`（百分比相对页宽；表格不会窄过里面最宽的一个字，一字宽的竖条写 1%–12% 都一样），真机字号 1.0 和 0.8 都竖排；其余 em 换算（行距、竖直间距、左右边距）仍按缺省字号。
